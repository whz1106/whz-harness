# AGC64F 大模型部署与推理操作手册

> 适用机器：AGC-64F（64 × DX8190 16GB，Ubuntu 22.04.5，内核 5.15.0-119-generic，176 逻辑核，503G 内存）
> 三个模型互斥：**同一时间只能跑一个**。换模型必须重新跑对应的一键脚本，脚本会自动清旧容器并切 nginx。

---

## 1. 这套部署长什么样

```
                客户端 / 压测
                     │
                     ▼
             Nginx  127.0.0.1:8000        ← 负载均衡入口（least_conn）
                     │
   ┌─────────────────┼─────────────────┐
   ▼                 ▼                 ▼
 d1/d2...          d3/d4...          g1/g2...     ← 每个实例 = 1 个 vLLM 进程
 Docker runtime    Docker runtime     Kata runtime
 (nvidia 驱动卡)    (nvidia 驱动卡)     (VFIO 直通卡)
```

- **d 实例**：`--gpus all` + `CUDA_VISIBLE_DEVICES`，跑在宿主 nvidia 驱动的 32 张卡上（host network，直接监听宿主端口）。
- **g 实例**：`--runtime io.containerd.kata.v2`，把 VFIO 直通的另外 32 张卡整卡透传进轻量虚拟机（guest 内 `vllm serve`，宿主端口映射）。
- **实例一旦混用 Docker/Kata，就不能跨侧做张量并行**：所以每个实例的卡必须整组落在同一侧（例如 70B 是 16 卡 TP=16，就拆成 d1/d2 各 16 张、g1/g2 各 16 张）。

## 3. 部署前检查

```bash
# GPU 数量（本机没有 nvidia-smi，统一用 dx-smi）
dx-smi -L | wc -l                 # 期望 32（宿主 nvidia 驱动可见的卡）
dx-smi --query-gpu=index,name,memory.total --format=csv | head

# 共享内存：模型服务要求 300G（启动脚本会自己 remount，这里只看现状）
df -h /dev/shm

# 容器运行时
docker ps                       # benchclient 应长期存在
docker images | grep dx-vllm    # 期望有 dx-vllm:0.21.0
command -v containerd-shim-kata-v2   # 跑 g 实例（Kata）时必须有软链

# nginx
nginx -v && systemctl is-active nginx

# 内核模块（Kata 侧 16 卡必需）
cat /sys/module/vhost/parameters/max_mem_regions    # 期望 >= 256
cat /etc/modprobe.d/vhost-vfio.conf                 # 期望 options vhost max_mem_regions=256
```

失败时的处理见第 10 节。

## 4. 一次性放置：脚本 + nginx 配置

```bash
# 4.1 启动脚本目录（三个脚本都读 /root/start-sh）
mkdir -p /root/start-sh
cp scripts/*.sh /root/start-sh/
chmod +x /root/start-sh/*.sh
ls -l /root/start-sh/

# 4.2 nginx 配置目录
cp nginx/*.conf /etc/nginx/conf.d/
nginx -t && systemctl reload nginx
```

**切换机制**：`nginx_switch.sh` 不直接改文件，而是把 `/etc/nginx/conf.d/active.conf` 做成指向某份配置的**软链**：

```bash
/etc/nginx/conf.d/active.conf -> /etc/nginx/conf.d/ds70b.conf
```

`nginx.conf` 里写的是 `include /etc/nginx/conf.d/active.conf;` —— **只加载 active.conf 这一份**，其余 `.conf` 不会被自动加载（四份配置里都有同名 `upstream vllm_backend`，若写成 `*.conf` 会直接报重复 upstream 起不来），所以换 profile 就是换这个软链。
手工切换等价于：

```bash
cd /etc/nginx/conf.d
rm -f active.conf && ln -s qwen122b.conf active.conf
nginx -t && systemctl reload nginx
```

或者用脚本：

```bash
/root/start-sh/nginx_switch.sh 122b    # 8 实例 8001-8008
/root/start-sh/nginx_switch.sh 70b     # 4 实例 8001-8004
/root/start-sh/nginx_switch.sh 35b8    # 8 实例 8001-8008
/root/start-sh/nginx_switch.sh 35b     # 16 实例 8001-8016
```

> 正常流程**不需要手动切 nginx**：三个一键启动脚本都会自己调 `nginx_switch.sh`。
> 同一个模型反复压测更不用动 nginx。

**先占检验**（推荐手工验一次）：

```bash
ss -lntp | grep :8000
curl -s --noproxy '*' http://127.0.0.1:8000/v1/models | head
```

## 5. 一键启动

```bash
# 35B：32 卡 / 8 实例 / TP=4（只用宿主 nvidia 卡）
bash /root/start-sh/Start_Qwen3.6-35B-A3B-FP8.sh

# 35B 额外再加 8 个 Kata 实例（16 实例 / 64 卡），默认关闭
ENABLE_KATA=1 bash /root/start-sh/Start_Qwen3.6-35B-A3B-FP8.sh

# 122B：64 卡 / 8 实例 / TP=8（4 个 Docker + 4 个 Kata）
bash /root/start-sh/Start_Qwen3.5-122B-int4.sh

# 70B：64 卡 / 4 实例 / TP=16（2 个 Docker + 2 个 Kata）
bash /root/start-sh/Start_DeepSeek-R1-Distill-Llama-70B.sh
```

脚本内部固定顺序：

1. 检查 `/data` 挂载 → 检查模型目录/config.json → 检查镜像 `dx-vllm:0.21.0` → 检查 `containerd-shim-kata-v2`（Kata 场景）
2. 解析 VFIO IOMMU 组（Kata 场景，缺 `/dev/vfio/N` 立刻报错退出）
3. `mount -o remount,size=300G /dev/shm`
4. `nginx_switch.sh <profile>` 切 nginx
5. 清理同名旧容器（只按名字：`d1..d8 g1..g8`）
6. 先起 Kata 实例（大内存先占），`sleep 20` 后执行 `remap_kata_vcpus` 修正 vCPU 亲和性
7. 再起 Docker 实例
8. 打印状态

可覆盖的环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `KATA_CPUS` | 35B:7 / 122B:15 / 70B:31 | Kata guest vCPU 数 |
| `KATA_MEM` | 35B:20g / 122B:48g / 70B:48g | Kata guest 内存（宿主 `/dev/shm` 会按 ×1.125 预占） |
| `KATA_NUMA_NODE` | 1 | Kata 卡所在 NUMA 节点 |
| `ENABLE_KATA` | 0（仅 35B） | 35B 是否额外起 g1–g8 |

## 6. 判断就绪

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'

# 每个实例应该是 1
for c in $(docker ps --format '{{.Names}}' | grep -E '^(d|g)[0-9]+$'); do
  echo "$c=$(docker logs $c 2>&1 | grep -c 'Application startup complete')"
done

# 每个后端自己健康检查
for p in $(seq 8001 8008); do
  printf "%s=%s " $p "$(curl -s -o /dev/null -w '%{http_code}' --noproxy '*' --max-time 2 http://127.0.0.1:$p/health)"
done; echo

# 聚合入口
curl -s --noproxy '*' http://127.0.0.1:8000/v1/models
```

- 日志里看到 `Application startup complete` = 该实例好了。
- 看实时日志：`docker logs -f d1`（Docker 实例）、`docker logs -f g1`（Kata 实例）。
- 大模型（70B FP16）加载 131 GiB 权重，约 10–15 分钟；官方口径"30 分钟"是留余量。

## 7. 推理调用

服务是标准 vLLM OpenAI 接口，聚合入口 `http://<机器IP>:8000`，单实例 `http://<机器IP>:8001` 等。

> 本机有 `http_proxy` 环境变量，**在宿主机上 curl 本地端口必须加 `--noproxy '*'`**，否则会走代理返回 502/超时。

### 7.1 curl（completions）

```bash
curl -s --noproxy '*' http://127.0.0.1:8000/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "Qwen3.6-35B-A3B-FP8",
    "prompt": "用一句话解释什么是张量并行。",
    "max_tokens": 128,
    "temperature": 0
  }'
```

`model` 字段填服务名（第 2 节表里那个），**不是路径**。

### 7.2 curl（chat）

```bash
curl -s --noproxy '*' http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "Qwen3.6-35B-A3B-FP8",
    "messages": [{"role": "user", "content": "你好，自我介绍一下"}],
    "max_tokens": 256,
    "temperature": 0
  }'
```

### 7.3 Python（OpenAI SDK）

```python
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY")

resp = client.chat.completions.create(
    model="Qwen3.6-35B-A3B-FP8",
    messages=[{"role": "user", "content": "你好"}],
    max_tokens=256,
    temperature=0,
)
print(resp.choices[0].message.content)
```

> 如果在宿主机上跑且 Python 也继承了 `http_proxy`，先 `export no_proxy=127.0.0.1,localhost`。

### 7.4 列表与健康

```bash
curl -s --noproxy '*' http://127.0.0.1:8000/v1/models   # 已加载的模型
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/health   # 200
```

## 8. 压测（vllm bench）

### 8.1 压测客户端容器（只需建一次，长期复用）

```bash
docker rm -f benchclient 2>/dev/null
docker run -d --pull never --name benchclient --network host \
  -v /data/models:/models --entrypoint /bin/bash dx-vllm:0.21.0 -c "sleep infinity"
```

**必须在独立的 `benchclient` 里跑**，不要在 d1/g1 里跑：压测进程和在线实例抢 CPU，高并发会被压掉 20~30%。

### 8.2 聚合压测（走 nginx 8000，日常就用这个）

```bash
docker exec benchclient vllm bench serve \
  --backend openai \
  --base-url http://127.0.0.1:8000 \
  --endpoint /v1/completions \
  --model /models/Qwen3.6-35B-A3B-FP8 \
  --served-model-name Qwen3.6-35B-A3B-FP8 \
  --dataset-name random \
  --random-input-len 128 \
  --random-output-len 1024 \
  --ignore-eos \
  --num-warmups 24 \
  --num-prompts 32 \
  --max-concurrency 32
```

把 `--model` / `--served-model-name` 换成对应模型，端口不变（聚合入口统一 8000）：

| 模型 | `--model` 与 `--served-model-name` |
|---|---|
| 35B | `/models/Qwen3.6-35B-A3B-FP8` / `Qwen3.6-35B-A3B-FP8` |
| 122B | `/models/Qwen3.5-122B-A10B-GPTQ-Int4` / `Qwen3.5-122B-A10B-GPTQ-Int4` |
| 70B | `/models/DeepSeek-R1-Distill-Llama-70B` / `DeepSeek-R1-Distill-Llama-70B` |

**每次只改三个参数**：

- `--random-input-len` 输入 token 数
- `--random-output-len` 输出 token 数
- `--num-prompts` 总请求数（一般设成并发数的整数倍）
- 要阶梯限并发就加 `--max-concurrency N`（配合 `--num-prompts` 用）

基线并发梯度（对应《AGC64F大模型性能测试结果整理.md》，`--random-input-len 128 --random-output-len 1024`）：

| 模型 | 并发梯度 |
|---|---|
| 35B | 8 / 64 / 128 / 256 / 512 / 768 / 896 |
| 122B | 8 / 128 / 256 / 384 / 512 / 768 |
| 70B | 4 / 32 / 128 / 256 / 384 |

### 8.3 单后端直连（确认某个实例本身能不能服务）

把 `--base-url` 换成单实例端口，只改 `--base-url`：

```bash
docker exec benchclient vllm bench serve \
  --backend openai \
  --base-url http://127.0.0.1:8003 \
  --endpoint /v1/completions \
  --model /models/DeepSeek-R1-Distill-Llama-70B \
  --served-model-name DeepSeek-R1-Distill-Llama-70B \
  --dataset-name random \
  --random-input-len 128 \
  --random-output-len 1024 \
  --ignore-eos \
  --num-warmups 3 \
  --num-prompts 1
```

端口对照：

| 模型 | Docker 实例 | Kata 实例 |
|---|---|---|
| 35B | 8001–8008 | 8009–8016（`ENABLE_KATA=1`） |
| 122B | 8001–8004 | 8005–8008 |
| 70B | 8001–8002 | 8003–8004 |

### 8.4 结果怎么读

`vllm bench serve` 末尾的输出里关注：

| 字段 | 含义 |
|---|---|
| `Output token throughput (tok/s)` | 输出吞吐，**对齐基线用的就是它** |
| `Total Token throughput (tok/s)` | 总吞吐（含输入） |
| `Mean TTFT (ms)` | 首 token 平均延时 |
| `Mean TPOT (ms)` | 平均每 token 耗时 |

## 10. 排障

### 10.1 `curl 8000/v1/models` 返回 **502 Bad Gateway**

99% 是**后端还没就绪**，不是 nginx 配错。确认：

```bash
docker ps                                       # 容器在不在
ss -lntp | grep -E ':800[0-9]'                  # 后端端口有没有在监听
for p in $(seq 8001 8008); do printf "%s=%s " $p \
  "$(curl -s -o /dev/null -w '%{http_code}' --noproxy '*' --max-time 2 http://127.0.0.1:$p/health)"; done; echo
docker logs d1 2>&1 | tail -3                   # 卡在 Profiling CUDA graph / 加载权重 = 还在初始化
```

后端端口全部没监听 → 等。日志出现 `Application startup complete` 后再请求。

### 10.2 `docker rm -f g1` 卡住 / 删不掉

Kata shim 进程还活着。**定向**清理（不要全局 pkill）：

```bash
docker ps --no-trunc                                 # 拿沙箱 ID
ps -eo pid,comm | grep containerd-shim               # 找 kata shim
kill -TERM <shim_pid>                                # 必要时 kill -9 <shim_pid>
# 再定向清 qemu/virtiofsd（用 /proc/<pid>/cmdline 确认是目标沙箱）
docker rm -f g1
df -h /dev/shm
```

### 10.3 Kata 实例起不来：`vhost_set_mem_table failed: Argument list too long (7)`

16 张 VFIO 卡直通时，guest 内存被 PCIe hole 切碎，超过 `vhost` 默认的 64 个内存区域。
修复（**不需要重启宿主**）：

```bash
echo 'options vhost max_mem_regions=256' > /etc/modprobe.d/vhost-vfio.conf
modprobe -r vhost_net vhost_vsock vhost
modprobe vhost
cat /sys/module/vhost/parameters/max_mem_regions   # 256
```

> 前提是当前没有 Kata 容器在跑（否则模块 busy）。执行前确认 `docker ps` 里没有 g* 容器。

### 10.4 Kata 实例吞吐明显偏低（guest CPU steal 高）

dx-gpu 版 Kata 会把**每个** sandbox 的 vCPU 线程钉到 node1 的前 N 个 CPU（44–59），多个 sandbox 全挤在同一组 CPU 上 → guest 内 `%st` 可达 47%，单实例吞吐腰斩。
启动脚本已经处理：起完 g 实例后 `sleep 20` 再调用 `remap_kata_vcpus`，把每个 sandbox 改钉到 node1 内**互不重叠**的 CPU 子集。

- 如果手工 `docker start g1` 重启了 Kata 容器，**需要重新执行一次启动脚本**来修亲和性。
- 检查：`docker exec g1 top -bn1 | head`，`%st` 应该是 0。

### 10.5 Kata 容器一直 `Created` 起不来（内存不够）

Kata guest 内存来自宿主 `/dev/shm`（tmpfs），QEMU 按 `-m × 1.125` 预留，且默认落在**同一个 NUMA node**（本机 node1 ≈ 252G）。

规则：`实例数 × KATA_MEM × 1.125 < node 容量`。

| 场景 | 计算 | 结论 |
|---|---|---|
| 35B 8 个 Kata × 20g | 8 × 20 × 1.125 = 180G | OK |
| 122B 4 个 Kata × 48g | 4 × 48 × 1.125 = 216G | OK |
| 70B 2 个 Kata × 48g | 2 × 48 × 1.125 = 108G | OK |

把 `KATA_MEM` 调大前先按这个公式算一遍。启动脚本会先 `mount -o remount,size=300G /dev/shm`。

### 10.6 端口/实例对照表速查

| 模型 | Docker 实例 | Kata 实例 |
|---|---|---|
| 35B（32 卡 / 8 实例） | 8001–8008 = d1–d8 | —（`ENABLE_KATA=1` 时 8009–8016 = g1–g8） |
| 122B（64 卡 / 8 实例） | 8001–8004 = d1–d4 | 8005–8008 = g1–g4 |
| 70B（64 卡 / 4 实例） | 8001–8002 = d1–d2 | 8003–8004 = g1–g2 |

`8000` 永远是 nginx 聚合入口。后端端口按启动脚本里的 `PORT` 递增规则分配，不会变。
