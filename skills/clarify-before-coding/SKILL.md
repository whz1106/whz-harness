# 澄清再动手（Clarify Before Coding）

## Overview

开发场景下优先「先对齐、再改代码」。目标不是拖慢交付，而是避免没理解意图就开干、没挖清根因就堆补丁、一次 PR 塞太多无关改动。

本 skill 是**软约束**：默认按下面流程走；若是显而易见的单行修复、用户已给完整可执行规格、或用户明确说「直接改」，可跳过或降级，并在回复里简短说明为何跳过。

## Typical Requests

- 「帮我修一下这个 bug / 加这个功能」但描述还粗
- Agent（含 OpenCode 等）刚想动手，用户希望先讨论计划
- 「先想清楚再改」「从第一性原理分析一下」
- 需要拆子任务、派多个 subagent，但父代理先当审查者

## Soft Principles

1. **对齐前不写业务代码**：讨论意图、根因、方案；确认计划后再改。
2. **第一性原理**：从问题本质出发，而不是从「看起来能改的地方」出发。
3. **苏格拉底式追问**：一次只问一个关键澄清问题，追到意图与约束大致清楚（约 95%），不要一次甩一长串问卷。
4. **一问题 ≈ 一小 PR**：不顺手扩 scope；无关优化另开议题。
5. **确认后可并行**：用户点头后可派多个 subagent 执行；父代理偏审查与整合。
6. **可降级**：场景不适合时跳过，不卡死流程。

## Workflow

### 1. 澄清意图（对齐前）

先判断：当前信息是否已够动手？

若不够，用苏格拉底追问补齐，优先问这些（每次一个）：

- 要解决的用户可见问题是什么？
- 成功标准 / 非目标是什么？
- 约束（时间、兼容、环境、不可改区域）？
- 已观察到的现象与复现路径？

不要假装听懂。不确定就问；问完用一两句复述确认。

### 2. 第一性原理：本质 → 根因 → 解法

在动手前产出一份简短计划（可口头或短 MD），至少覆盖：

| 项 | 写什么 |
| --- | --- |
| 问题 | 用户感知到的现象与影响 |
| 本质 | 去掉表象后，真正在约束什么 |
| 根因 | 为什么会出现（证据或可检验假设） |
| 解法 | 改什么、为什么这是最小有效改动 |
| 取舍 | 备选方案与为何不选 |
| 风险 | 可能破坏什么、如何回滚 |
| 验证 | 怎么证明修好了（命令、场景、预期） |
| 范围 | 本 PR 包含 / 明确不包含 |

根因未立住时，不要用「再加一层判断 / 再加个开关」当默认解。

### 3. 等用户确认

把计划亮出来，等用户确认（口头同意即可）。未确认前：

- 可以读代码、搜证据、写计划
- **不要**改业务代码、开正式修复 PR、大规模重构

用户确认后进入执行。

### 4. 执行（可派 subagent）

确认后：

1. 按计划拆成可并行的小任务（若值得）
2. 可派多个 subagent 做实现 / 测试 / 文档等窄任务
3. **父代理当审查者**：核对是否偏离计划、scope 是否膨胀、验证是否做过
4. 中途若发现根因判断错了：停手，更新计划，再跟用户对齐，再改

### 5. 小步提交与 PR

- 分支命名遵循仓库习惯（常见 `feat/<slug>` / `fix/<slug>`）
- 一次 PR 只打一个问题；大改动拆多个 PR
- 与 `git-pr-workflow` 配合：中文 commit / PR，精确 stage，rebase 到目标分支

**PR 描述必须覆盖**（可用小节标题）：

```markdown
## 问题
…

## 根因
…

## 解法
…

## 验证
…
```

可选补充：风险 / 回滚、非目标、与计划的差异（若有）。

## Soft Downgrade

下列情况可跳过完整澄清，直接小改并说明理由：

- 用户已给出完整规格且边界清楚
- 单行笔误 / 明显 typo / 纯格式
- 用户明确说「别问了，直接改」
- 紧急热修且用户接受事后补计划（事后仍应在 PR 写清问题/根因/解法/验证）

## Anti-Patterns

- 没复述意图就开始大改
- 只治症状（多加 if）却不谈根因
- 「顺便」重构、改无关文件、扩大依赖面
- PR 只有「fix bug」没有问题/根因/验证
- 把软约束当成死锁：场景不适合仍反复追问不放行

## Composition

- 提交与 PR 流程：配合 `git-pr-workflow`
- 审查阶段：可再开 `adversarial-code-review` 做对抗式检查
- 提示词心法对照：苏格拉底追问、第一性原理；需要压测方案时可叠加「预演失败」
