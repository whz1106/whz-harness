# 对抗式 Code Review（Adversarial Code Review）

## Overview

以**反对者**立场审查变更：默认「这版改动可能有问题」，要用证据才能放过或否定。目标是找出真实风险，不是堆严厉语气，也不是帮作者圆场。

「通过」是合法结论。找不到问题时不要编；但「通过」也必须写清查了什么范围。小改动可以缩短输出，两层提问和合并后影响仍要过一遍，不要无证据直接说「没问题」。

## Typical Requests

- 「帮我 review 这个 PR / 这段 diff」
- 「站在反对者角度挑刺」
- 「合并前看看会不会埋雷」
- 父代理审查 subagent 提交的改动

## Stance

1. **默认对抗，但允许通过**：不假设作者正确；指出问题要有 diff / 行为 / 测试上的依据。没有依据就不要把口味写成缺陷。
2. **三件事都要想一遍**：
   - **规格与规范**：是否按 issue / 验收标准实现；是否违反仓库已写明的规范。
   - **本 PR 自身**：逻辑、做法、边界、测试、可读性有什么问题？
   - **合并之后**：会引入哪些新问题（回归、耦合、运维、安全、性能、后续维护成本）？
3. **只审查**：默认只给结论与修改建议；**除非用户明确说「按你的意见改」**，否则不擅自改代码。
4. **辩论 + 预演失败**：主动攻击方案弱点，看反方论点是否被证据化解；假设已合并上线，设想 2～3 个最可能的失败路径（错误输入、并发、空数据、权限、回滚困难等），看本 PR 是否挡住。

## Karpathy 四点（输出里要留下痕迹）

不必打分，但审查结束时下列四点都要在输出中看得见，不能只在心里过一遍：

| 条 | 问什么 |
| --- | --- |
| 假设 | 作者默认了什么？这些假设在代码/环境里成立吗？ |
| 简单 | 有没有更简单、同效的做法？复杂度是否与问题匹配？ |
| 手术式改动 | 是否只改该改的？有无顺手重构、无关文件、scope 膨胀？ |
| 目标可验证 | 成功标准是否清楚？现有测试/验证步骤能否证明？ |

## Review Dimensions

按需覆盖（与改动相关的优先）：

- 正确性与根因是否对症（是否只治症状）
- 边界条件、错误处理、空值/并发/重试
- 安全（注入、权限、密钥、不可信输入）
- 性能与资源（热路径、N+1、无界增长）
- 可读性与命名、模块边界
- 测试缺口与验证是否可复现
- 兼容性 / 迁移 / 特性开关
- 可观测性（日志、指标、失败是否可诊断）

## 严重度判定

| 级别 | 含义 | 默认归入此类（有证据时） |
| --- | --- | --- |
| 致命 | 必须修才能合 | 可利用的安全问题（注入、越权、密钥泄露）；可能丢数据或不可逆迁移且无法回滚；主路径行为错误；测试跑不通或与改动主张矛盾；明确验收标准被漏做或做错 |
| 重要 | 强烈建议修，带着合风险高 | 重要分支缺测试、较可能的回归、明显的 scope 膨胀、热路径性能问题、常见输入缺少错误处理、失败后难以诊断 |
| 建议 | 可选改进，不阻塞合并 | 命名、结构、小幅可读性、非阻塞的重构或注释 |

补充规则：

- **风格偏好不能当作致命缺陷。** 未写入仓库规范的口味，最多进「建议」。
- 仓库规范：文档自己定了级别就按文档；否则，已写明的规则违反算「重要」，未成文的习惯算「建议」。
- 在「重要」和「建议」之间拿不准时，选「建议」，必要时标 `[推测]`。
- 不要为了显得严格而捏造致命项。

## Output Format

用中文，结构固定，便于扫读：

```markdown
## 审查范围
- 对比点：`<base>` ... `<HEAD>`（写明 SHA / 分支 / tag）
- 规格来源：issue / PR 描述 / 验收标准 / 无
- 仓库规范：读了哪些文件；没有则写「未发现」

## 变更主张
（作者声称解决了什么；根因与解法是否自洽）

## 结论
通过 | 要改 | 再讨论
（一句话说明为什么）

## 四点对照
- 假设：…
- 简单：…
- 手术式改动：…
- 目标可验证：…

## 规格与规范
- …（缺漏、跑偏、做错，或违反已写明的规范；没有则写「无」）

## 致命
- …（必须修才能合；写清位置/证据/风险）

## 重要
- …（强烈建议修；写清原因）

## 建议
- …（可选改进，不阻塞）

## 合并后风险（预演失败）
- …（合并后可能出现的新问题）

## 测试缺口
- …（缺什么用例 / 怎么补验证）

## 待作者澄清的问题
- …（阻塞判断、需要作者补充的事实）
```

规则：

- **没有某类问题时**：写「无」或省略该节，不要凑数。「待作者澄清的问题」没有就省略。
- **每条意见尽量带锚点**：文件、符号、行为路径，或引用 diff 片段。
- **区分事实与推测**：不确定标 `[推测]`，并写还需要什么证据。
- 结论为「通过」时，仍可列少量建议；「审查范围」和「四点对照」仍要写。
- 关键判断依赖缺失证据（测没跑、复现不了、没有 issue/验收标准且行为对错说不清）时，结论用「再讨论」，不要硬判「通过」或「要改」。

## Workflow

1. **先钉死对比范围**：默认是目标分支（`main` / `master` / 仓库默认分支）与该 PR 的 merge-base，到当前 `HEAD`；用户指定了 commit / 分支 / tag 则用指定值。在输出里写明对比点。用实际 diff（如 `gh pr diff`、`git diff <base>...<HEAD>`），不要只看标题或文件列表。
2. **收集规格**：issue、PR 描述、验收标准、关联工单。没有就在「规格来源」写「无」，不要假装有规格。
3. **读取仓库约束**：`AGENTS.md`、`CONTRIBUTING.md`、`CODING_STANDARDS`、项目内审查/规范文档等。其中已写明的规则是硬约束，覆盖个人口味。
4. 先复述作者声称解决了什么，根因/解法是否自洽。
5. 先做规格轴：是否缺漏、跑偏、做错；再审本 PR 内的正确性与做法。
6. 再审合并后新问题，并做预演失败。
7. 对照 Karpathy 四点，按严重度规则归入致命 / 重要 / 建议。
8. 给出结论。若用户要你修，再另开实现流程（可配合 `clarify-before-coding` 与 `git-pr-workflow`）。

大 PR：按目录或风险面拆开审，再汇总；不要只给印象分。可以并行分头审，但必须先统一对比点和规格来源。

自审：若审查者自己写了改动中的实质部分，必须在「审查范围」里说明，并建议另找审查者。若仍继续自审，更要找反例，不要给无证据的「通过」。

纯文档错字、单行重命名等可以写短评，仍要给出对比点，并扫一眼合并后影响。

## Anti-Patterns

- 没钉死对比范围就开始审，或只根据标题/文件列表下结论
- 不对照 issue / 验收标准，只看代码是否「写得干净」
- 客气到只说「整体不错」却无任何具体检查痕迹
- 风格偏好冒充致命缺陷
- 只挑命名/格式，不碰逻辑、规格与合并后风险
- 未受请求就直接改作者分支
- 把清单当成必须填满的表格（无问题硬写三条）
- 自审却不声明，并直接「通过」

## 对照样例（标定分级，不是真实 PR）

**应结论为「通过」**：对比点 `abc123...def456`，只把一个内部函数重命名，调用点已全部更新，现有测试通过，无规格变更。四点对照应体现假设成立、改动手术式、可用现有测试验证。建议可省略或只留文档用词，不得编造致命项。

**应结论为「要改」**：对比点同上，新增支付回调处理；issue 要求按订单号幂等入账，实现却每次回调直接入账且无去重，也没有重复回调测试。应归入致命（主路径可能重复入账），合并后风险写网络重试导致重复记账，测试缺口写缺少重复回调用例。

## Composition

- 开发澄清与小 PR：`clarify-before-coding`
- 提交/PR 规范：`git-pr-workflow`
- 需要作者补计划时：要求 PR 描述含 问题 / 根因 / 解法 / 验证
